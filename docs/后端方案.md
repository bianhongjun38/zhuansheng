# 后端方案 v2 · 20 人小圈子

> **✅ 已上线（2026-10-27）**：后端跑在自己的阿里云 ECS 上，不再依赖 Cloudflare。
> 
> | 项 | 值 |
> |---|---|
> | 公网地址 | `http://8.156.78.63:8081` |
> | 健康检查 | `GET /health` |
> | 部署位置 | `/opt/zsb-api/`（systemd 服务 `zsb-api`）|
> | 存储 | 本机 SQLite `/opt/zsb-api/data/zsb.db` |
> | 备份 | 每天 03:30 自动，`/opt/zsb-api/backups/`，留 14 份 |
> | 端到端测试 | 19/19 通过（含公网）|
> 
> 为什么从 Cloudflare 换过来：Workers 全球 1101 故障时全挂过一次，
> 而且数据在自己手里查起来更直接。20 人的量（20 × 23KB ≈ 460KB）本机 SQLite 绰绰有余。
> 流量实测：20 人 × 每天 5 次同步 ≈ **85 MB/月（最坏）～0.3 MB/月（现实）**，
> 占阿里云 20 GB 免费额度的 0.41% ~ 0.001%，可以忽略。

## 一、20 人这个数字改掉了什么

实测配额对照（`build/probe20.py`）：

| 项目 | 20 人实际 | 免费额度 | 占用 |
|---|---|---|---|
| 写入行/天（全量快照，10 人） | 3,370 | 100,000 | 3.4% |
| 进度存储上限 | 460 KB | 5 GB | 0.009% |
| 英语成绩一年 | 219,000 行 ≈ 42 MB | 5 GB | 0.8% |
| 请求数/天 | 30 | 100,000 | 0.03% |

**结论：额度完全不是问题，全量快照同步都行。**
上一版担心的「增量同步、逐条 UPDATE 改造」是纯为了 1000 人准备的，**全部删掉**。

### 但有个坑必须说清楚：KV 不能用

我查了官方 limits（`developers.cloudflare.com/kv/platform/limits/`）：

```
Workers KV（免费版）
  Reads              100,000 / 天
  Writes to different keys  1,000 / 天   ← 关键
  Writes to same key          1 / 秒
```

20 人 × 每天同步 3 次 = **60 次写入/天**，看着没问题。
但如果按「一行一个 key」存（每个勾选项一个 key），一次同步就是 337 次写入 —— 一个人同步 3 次就打满 1000 的额度。

而 **D1 免费版每天 10 万行**，337 行全量写进去占 0.34%。而且还白送两样东西：

- **7 天 Time Travel 回滚**（免费版就有）
- SQL 聚合，排行榜一条 `GROUP BY` 搞定

**所以选 D1，不选 KV。**

## 二、账号：用户名 + 密码

> 早期这里是「用户名直登，不做任何验证」。后来你明确要求
> 「登陆还是加个密码吧，显示用户名啊，又不是外人」——本节按这个改了。
> 排行榜显示真实用户名不变。

```
POST /v1/register { username: "小明", password: "xxxx" }
POST /v1/login    { username: "小明", password: "xxxx" }
  → { ok: true, uid, username, token, isNew }
```

- **用户名唯一**，重名注册返回 `name_taken`，换一个
- 密码走 **PBKDF2-SHA256 / 10 万轮 / 每用户独立 16 字节 salt**，服务端不存明文
- 登录成功发一个随机 `token`（24 字节 hex），客户端只存 token，**不存密码**
- 之后请求带 `Authorization: Bearer <token>`
- **每次登录都换新 token**：换手机后旧手机的 token 立刻失效。
  这既是「换手机」也是「改密码后踢掉其他设备」，一个机制解决两件事
- **忘记密码 = 找管理员重置**。20 个人，写「找回密码」流程的收益远小于成本

**为什么还是不做验证码/邮箱**：20 个同学都在一个群里，防陌生人不是需求，
防「误操作丢数据」才是。密码是为了防止别人手滑登进你的账号改数据，
不是为了对抗攻击者。

**排行榜显示真实用户名**（`users.username`），不做匿名化——你说过「又不是外人」。

## 三、数据模型（砍完只剩 3 张表）

```sql
-- 1. 用户
CREATE TABLE users (
  uid        TEXT PRIMARY KEY,      -- 随机 UUID
  username   TEXT NOT NULL,         -- 显示名，可重名
  token      TEXT NOT NULL UNIQUE,  -- 手机存的凭证
  created_at INTEGER NOT NULL,
  last_seen  INTEGER NOT NULL
);

-- 2. 学习进度：一个用户一条记录，整包 JSON
CREATE TABLE progress (
  uid         TEXT PRIMARY KEY,
  data        TEXT NOT NULL,        -- 就是 exportJson() 的 state 部分
  plan_ver    INTEGER NOT NULL,     -- 计划的版本，用于冲突提示
  updated_at  INTEGER NOT NULL
);

-- 3. 英语闯关成绩
CREATE TABLE eng_round (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  uid        TEXT NOT NULL,
  day        TEXT NOT NULL,         -- 服务端按 Asia/Shanghai 切日
  right_cnt  INTEGER NOT NULL,
  wrong_cnt  INTEGER NOT NULL,
  ms         INTEGER NOT NULL,
  started_at INTEGER NOT NULL,
  client_rev TEXT NOT NULL,         -- 幂等键
  UNIQUE(uid, client_rev)
);
CREATE INDEX idx_eng_day ON eng_round(day, right_cnt DESC);
```

**注意我把 progress 改回了 JSON blob**。上一版拆成 337 行是为了「以后做同专业统计」，
20 人根本不需要那种分析，blob 让同步代码从「一堆 UPSERT」变成「一次 UPDATE」，少一半 bug。

**数据量**：20 人 × 23 KB = **460 KB**，一个查询全取出来都不心疼。

## 四、三个接口

| 接口 | 作用 |
|---|---|
| `POST /v1/login` | 用户名换 token |
| `POST /v1/sync` | 上传进度，返回服务端版本（带冲突检测） |
| `POST /v1/eng/round` | 上报一轮成绩 |
| `GET /v1/eng/board?range=day\|week` | 排行榜 |

### 同步的冲突处理（20 人也不能想当然）

关键问题：**手机 A 和手机 B 都有数据怎么办**？

上一版用单向版本号，会丢数据。20 人场景正确做法：

```
POST /v1/sync { data, updatedAt, planVer }
```

- 服务端比较 `updatedAt`：比库里的新就覆盖，旧就返回服务端版本让客户端决定
- **客户端不自动覆盖**。弹一句：
  「云端进度比这台手机新（3 小时前），要用云端的还是用手机的？」
  两个按钮，用户按一下。

20 个人，一年也用不了几次，弹一次窗口比写一套自动合并靠谱得多。

## 五、排行榜

```sql
SELECT u.username, SUM(r.right_cnt) AS score, COUNT(*) AS rounds
FROM eng_round r JOIN users u ON u.uid = r.uid
WHERE r.day = ?
GROUP BY r.uid
ORDER BY score DESC, rounds ASC
LIMIT 50;
```

同分时轮数少的靠前。周榜换 `day BETWEEN`。

### 防作弊：20 人不需要那套东西

上一版我写了三层防作弊、每日种子校验、服务端重跑判分 —— **那是防陌生人的，这里是同学，全部删掉**。

只留一条最便宜的：

```
right_cnt + wrong_cnt <= 50      -- 单轮题数上限
ms >= (right_cnt+wrong_cnt)*800  -- 每题至少 0.8 秒
```

挡掉手滑和明显离谱的数字就够了。真有同学想刷榜，改 APK 你也能看出来——20 个人的榜，谁突然一天涨 5000 分，一眼就假。

## 六、上线后真正的收益：数据能找回了

这才是你最初说的那个痛点。D1 免费版白送的 **7 天 Time Travel**：

```bash
# 出事时回到 1 小时前
npx wrangler d1 time-travel restore zsb-data --timestamp=<ISO时间>
```

加上应用层兜底：每次 `POST /v1/sync` 覆盖前，把旧值写进 `progress_history`（保留最近 10 版）。

这解决的是「同学误操作清空进度」「我改坏了数据」这类问题，而**这才是 20 人场景真实的风险**。

## 七、实施顺序

### 阶段 0：本地自动备份（不依赖后端，今天就能做）

每天首次打开时把快照写进 `Downloads/zsb-backup/YYYY-MM-DD.json`，保留 30 天。

**这一步和后端无关，但能立刻解决 80% 的「数据丢了找不回」。**
